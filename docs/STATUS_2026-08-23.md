## 3. What has been built

### Stage 1 — Robotics (`sim/go2_sim/`)

A complete ROS 2 package simulating the Go2 Edu with the paper's sensor suite.

```
sim/go2_sim/
  urdf/go2_sim.urdf.xacro     Go2 body + Helios-32-class 3D LiDAR + RGB-D + IMU
  worlds/construction_scenario_{A,B,C}.world   generated, do not hand-edit
  config/scenarios.yaml       ← SINGLE SOURCE OF TRUTH (see below)
  config/nav2_sim_params.yaml Nav2 tuned for the Go2 footprint
  launch/gazebo.launch.py     Gazebo + robot + sensors + cmd_vel bridge
  launch/slam.launch.py       RTAB-Map (paper config) OR slam_toolbox (light)
  launch/nav.launch.py        Nav2: Dijkstra planner + DWB controller
  launch/inspection.launch.py all of the above, staged
  go2_sim/frame_capture.py    1 fps capture + ground-truth labelling
  go2_sim/waypoint_mission.py drives the route via Nav2 FollowWaypoints
  go2_sim/cmd_vel_bridge.py   stands in for the real go2_cmd_processor
```

**`config/scenarios.yaml` is the important file.** It encodes all 20 hazards
from the paper's Table 1 (A=5, B=7, C=8) with their OSHA citations and world
coordinates, and it drives three things at once: the Gazebo world generation,
the robot's inspection route, and the per-frame ground-truth labels. Change a
hazard there and everything downstream follows.

> Table 1 in the paper enumerates A1–A5, B1–B7, C1–C8 (5/7/8), but the prose in
> Section 5 says "A=5, B=6, C=7". I followed the table.

**Fidelity choices worth knowing:**

- **Locomotion is `planar_move`, not simulated legs.** On the real robot, Nav2
  publishes `/cmd_vel` and `go2_cmd_processor` converts it to a Unitree
  SportMode request — so from the navigation stack's point of view the Go2 is
  already a velocity-commanded base. Simulating 12 joints of legged contact
  dynamics would not change any SLAM or Nav2 behaviour and would cost more CPU
  than this machine has. The ROS interface is identical to hardware.
- **`cmd_vel_bridge` is deliberately kept in the loop** (with the real node's
  0.25 s watchdog and velocity clamps), so Nav2 limits tuned here are the limits
  the physical robot would see.
- **LiDAR is reduced to 16 beams × 440 samples @ 5 Hz** (a full Helios-32 sweep
  is ~29k CPU rays). Pass `lidar_beams:=32 lidar_samples:=900` on a GPU machine.
- **Global planner is NavFn with `use_astar: false`** — i.e. Dijkstra, exactly
  as Section 3.2 specifies.

The hazards are built from primitives arranged to reproduce the *spatial
relationship* that constitutes each violation — a cord lying **in** a puddle, a
load raised **on** forks, a ladder leaning **against a machine**. That relational
geometry is what the VLM has to read.

Safety signs are rendered as real textures with legible ANSI Z535 wording,
because Section 5 says sign text materially helps the VLM and that removing
signs is part of what makes scenarios B and C harder.

### Stage 3/4 — AI pipeline (`pipeline/`)

```
pipeline/
  config.py          per-layer model/effort config, pricing, key loading
  claude_client.py   SDK wrapper: on-disk cache, cost accounting, refusal handling
  rag.py             BM25 retrieval over the OSHA corpus  ← TESTED, WORKS
  prompts.py         B1–B4 + baseline prompts (paper's P1–P5 techniques)
  rules/osha_corpus.md  28 OSHA 29 CFR 1926 chunks
```

Layer mapping versus the paper:

| Layer | Paper | Here |
|---|---|---|
| B1 Perceptual Abstraction | Gemma-3 12B VLM | Claude (vision) |
| B2 Regulation Extraction | Llama-3.3 + RAG | Claude (text) + BM25 RAG |
| B3 Safety Assessment | Gemma-3 12B VLM | Claude (vision) |
| B4 Report Generation | DeepSeek-R1 | Claude, higher effort |

> **This trades away the paper's privacy argument.** Section 4.3 chose local
> open weights specifically so site imagery never leaves the site. Using a cloud
> API is the deliberate difference in this reproduction (you have no GPU
> cluster), not an oversight.

The retriever is lexical (BM25 + a synonym table bridging VLM vocabulary like
"puddle" to regulatory vocabulary like "wet location"), not embeddings —
28 chunks is too few for dense retrieval to earn its keep, safety regulation is
keyword-driven, and lexical retrieval is inspectable, which is the paper's whole
point about traceability.

### 4.2 — RESOLVED: CycloneDDS killed the entire Nav2 stack

**Symptom:** every Nav2 node died instantly with
`rmw_create_node: failed to create domain, error Error`, while Gazebo and SLAM
kept running happily. It looked like a Nav2 configuration bug. It was a
transport bug.

**Cause:** `ROS_LOCALHOST_ONLY=1` combined with `rmw_cyclonedds_cpp` on this WSL
distro.

**Measured**, with 8 nodes started at once:

| Configuration | Nodes surviving |
|---|---|
| cyclonedds, default | **8/8** |
| cyclonedds + my custom XML | 0/8 |
| fastrtps, default | 8/8 |
| fastrtps + `ROS_LOCALHOST_ONLY=1` | 8/8 |

My first fix — a custom `cyclonedds.xml` pinning to `lo` — failed just as hard,
because the `<Interfaces>` element it used is newer syntax that the Cyclone
version in Humble rejects, and a rejected config fails identically.

**Fix applied:** `scripts/ros_env.sh` now unsets `ROS_LOCALHOST_ONLY`, unsets
`CYCLONEDDS_URI`, and sets `ROS_DOMAIN_ID=42`. The XML was deleted.

If you ever see nodes dying on "failed to create domain", check those env vars
first.

### 4.5 — RESOLVED: scene quality was bad for a VLM

First captured frame was washed out to near-white, and the ladder geometry was
visibly wrong — my rail rotation was a hack rather than correct maths.

- **Ladder:** an SDF cylinder runs along its own +Z and RPY composes as
  `Rz(yaw)Ry(pitch)Rx(roll)`, so RPY `(0, tilt, yaw)` points it up the ladder
  axis. Rungs are the same construction at `pitch=π/2, yaw+π/2`. Fixed, and the
  cords use the same convention now.
- **Lighting:** ambient 0.55 → 0.33, dimmer sun/fill, darker floor. Too much
  ambient washes out exactly the colour cues (hi-vis orange, yellow hard hat,
  red brick) the VLM needs.
- **Camera:** raised to 0.10 m above the trunk and pitched ~7° up. At trunk
  height the lower half of every frame was bare floor.

Previews are in `results/preview/`.

### 4.7 — OPEN (blocking Stages 3–4): no API key

`ANTHROPIC_API_KEY` is not set, and there is no `ant auth login` profile.

**To unblock**, create `.env` at the repo root:

```
ANTHROPIC_API_KEY=sk-ant-...
```

`pipeline/config.py:load_api_key()` reads that automatically. (The SDK can also
use an `ant auth login` profile with no key set at all.)

**Cost warning — please read before running the full thing.** The paper's
dataset is 442 frames. This pipeline makes **3 model calls per frame** (B1, B2,
B3), two of which include an image, plus one B4 call per run, plus one baseline
call per frame if you want the comparison.

Rough estimate at Opus 5 rates (\$5/M in, \$25/M out): **~\$0.06/frame**, so
**~\$27** for a full 442-frame three-scenario run, roughly double with the
baseline comparison.

Mitigations already built in:
- Every response is cached on disk by request hash, so re-running after
  changing one layer does not re-pay for the others, and a crash does not
  re-pay for completed frames.
- Per-layer model config in `config.py` — you can put a cheaper model on B1/B2
  and keep the expensive one on B3, which is the layer the paper actually
  scores.

I defaulted to `claude-opus-5` everywhere. **Downgrading is your call, not
mine** — say the word and I'll switch it.

### 4.8 — OPEN: real-world dataset not yet downloaded

Your prompt asked for a construction-site dataset. Best candidate found:

**`keremberke/construction-safety-object-detection`**
(https://hf.co/datasets/keremberke/construction-safety-object-detection)

Why this one: its labels include `hardhat`, `no-hardhat`, `safety vest`,
`no-safety vest`, `person`, `excavators`, `barricade`. Those **negative** classes
are the key — they let per-image safe/unsafe ground truth be derived
automatically, which is what makes precision/recall computable on real imagery
without hand-labelling. It is also small (<1K images), which keeps API cost
sane.

Alternative: `Francesco/construction-safety-gsnvb` (1K–10K, parquet, COCO).

Not downloaded yet. This was sequenced after Stage 1 per your prompt's ordering.
